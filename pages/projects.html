Projects

반복 업무의 맥락을 유지하기

Projects는 특정 업무나 주제의 대화를 묶고, 반복되는 지시와 기준을 유지하며 팀과 결과를 공유하는 데 유용합니다. 파일 첨부 없이 운영할 때는 프로젝트 지시문, 맥락 메모, 결정 기록, 일정 실행 결과를 텍스트로 관리합니다.

첨부 불가 전제

프로젝트를 파일 저장소처럼 쓰지 않습니다. 문서 원본은 사내 저장소에 두고, ChatGPT에는 요약 맥락과 필요한 발췌만 텍스트로 제공합니다.

반복 보고

주간 보고, 운영 리뷰, 프로젝트 업데이트처럼 형식이 반복되는 업무에 적합합니다.

팀 기준 유지

용어, 톤, 품질 기준, 금지 표현을 프로젝트 지시문에 넣어 일관성을 유지합니다.

장기 조사

주제별 리서치 질문, 발견한 출처, 결정사항을 대화 단위로 이어갑니다.

구조

프로젝트는 폴더보다 작업 규칙에 가깝다

구성 요소 넣을 내용 첨부 없이 쓰는 방식
프로젝트 지시문 역할, 톤, 산출물 형식, 보안 주의점 “주간 런칭 리스크 리뷰”처럼 프로젝트 목적, 기본 표 형식, 금지 표현을 고정합니다.
맥락 메모 현재 상황, 이해관계자, 최근 결정, 참고 URL 제품명은 B제품, 고객명은 A사처럼 가명 처리하고 최근 결정 5개만 요약해 둡니다.
대화 스레드 업무별 질문과 결과 “고객 공지 초안”, “QA 재테스트 범위”, “영업 FAQ”처럼 산출물별로 대화를 나눕니다.
결정 기록 확정 사항, 보류 사항, 다음 액션 답변 끝에 날짜, 결정, 담당자, 근거, 다음 확인 질문을 결정 로그로 남기게 합니다.

팀 공유

공유 프로젝트를 팀의 결과 허브로 만든다

Enterprise 사용자는 개인 또는 워크스페이스 그룹을 프로젝트에 초대하고 Chat 또는 Edit 권한을 줄 수 있습니다. 공유 프로젝트의 구성원은 프로젝트 안의 대화와 현재 지시문을 함께 볼 수 있으므로, 반복 실행 결과를 날짜별 대화로 남기면 같은 맥락에서 후속 작업을 이어갈 수 있습니다.

역할 권한 추천 대상 운영 규칙
Owner 지시문, 구성원, 권한, 프로젝트 전체 관리 업무 책임자 또는 프로젝트 챔피언 일정과 결과 대화의 이름, 검토자, 보존 기준을 정합니다.
Edit 지시문과 프로젝트 맥락을 업데이트하고 구성원을 초대 실제 운영 담당자와 백업 담당자 공통 지시문 수정은 변경 이유와 날짜를 결정 로그에 남깁니다.
Chat 프로젝트 대화와 결과를 보고 새 질문을 실행 결과 소비자와 검토자 원본 결과는 보존하고, 다른 관점은 Branch 대화에서 검토합니다.

Project + Scheduled Tasks

매일 실행하고, 같은 프로젝트에서 검토한다

프로젝트는 맥락과 결과를 보관하고 Scheduled Tasks는 정해진 시간에 작업을 실행합니다. 작업 소유자는 실행 알림을 받고, 팀원은 공유 프로젝트의 고정 결과 대화에서 결과와 후속 질문을 확인하는 방식이 가장 단순합니다.

1

결과 대화 고정

“일일 시장 브리핑”처럼 용도별 대화를 만들고 날짜, 변화, 근거, 다음 액션 형식을 고정합니다.

2

맥락 스냅샷 작성

목적, 관심 주제, 제외 출처, 기준 수치, 팀 용어를 20줄 이내 텍스트로 일정 프롬프트에 넣습니다.

3

매일 실행

평일 오전처럼 실행 주기를 정하고, 변화가 없으면 짧게 종료하도록 조건을 둡니다.

4

크레딧 게이트

일정은 Deep Research나 이미지 생성을 바로 실행하지 않고, 필요한 경우 실행용 프롬프트만 제안합니다.

5

팀 검토와 Branch

팀원은 결과를 읽고 추가 분석이 필요하면 원본을 유지한 채 Branch에서 검토합니다.

일정 작업의 중요한 제약

프로젝트에 파일이 있더라도 Scheduled Tasks가 그 프로젝트 파일에 접근하지 못할 수 있습니다. 이 가이드는 애초에 첨부를 사용하지 않으므로, 일정에 필요한 기준과 맥락을 프롬프트 자체에 완결된 텍스트로 넣습니다. 팀 전원에게 자동 알림이 간다고 가정하지 말고, 프로젝트 링크와 결과 대화 이름을 팀 채널에 고정합니다.

운영 루틴

프로젝트가 커질수록 정리 규칙이 중요하다

1

주제별 생성

팀 전체가 아니라 반복 업무 단위로 프로젝트를 만듭니다.

2

지시문 갱신

잘 맞는 출력 형식과 금지 조건이 생기면 프로젝트 지시문에 반영합니다.

3

주기적 요약

긴 대화는 결정사항, 남은 질문, 다음 액션으로 요약해 새 대화의 출발점으로 씁니다.

복사해서 쓰기

프로젝트 지시문 템플릿

이 프로젝트의 목적: B제품 출시 전 리스크, 고객 공지, QA 재테스트 액션을 한 곳에서 관리
주요 사용자: PM, QA 리드, 법무 담당자, 고객지원 리드
반복 산출물:
- 주간 리스크 리뷰 표
- 고객 공지 초안
- QA 재테스트 체크리스트
- 영업/고객지원 FAQ
파일 첨부는 사용하지 않는다. 사용자가 붙여넣은 텍스트, 공개 URL, 직접 요약한 맥락만 근거로 작업한다.
항상 지킬 기준:
- 고객명은 A사/B사, 제품 내부 코드는 B제품처럼 가명 처리
- 미확정 일정과 수치는 “확인 필요”로 표시
- 법무/보안 판단이 필요한 문장은 별도 열에 표시
- 결과는 바로 업무 문서에 옮길 수 있게 표 또는 bullet로 작성
기본 출력 형식:
1. 이번 요청의 핵심 요약 5줄
2. 결정사항 / 보류사항 / 담당자 / 마감 / 근거 표
3. 리스크와 반론
4. 다음 액션과 추가 질문

Project와 일정 연결

매일 공유할 결과 프롬프트

작업 이름: B제품 출시 일일 리스크 브리핑
실행 일정: 매주 월요일부터 금요일까지 오전 8시 40분
결과를 확인할 프로젝트 대화: “01_일일 리스크 브리핑”

고정 맥락:
- 출시 목표일은 9월 15일이며 미확정 변경은 “확인 필요”로 표시
- 확인 영역은 QA 재테스트, 법무 승인, 고객 공지, 고객지원 FAQ
- 고객명, 매출, 내부 코드명은 가명 처리
- 파일과 프로젝트 파일을 근거로 사용하지 않음
- 공개 URL과 이 프롬프트 안의 텍스트만 사용

매일 할 일:
1. 공개된 변경 사항과 이전 실행 대비 달라진 점만 확인
2. 영향도 상/중/하와 근거 URL을 표로 정리
3. 변화가 없으면 “중요 변화 없음”과 확인한 범위만 5줄 이내 작성
4. 담당자가 오늘 확인할 질문을 최대 5개 제안
5. 추가 조사가 필요하면 Deep Research를 직접 실행하지 말고 아래 형식의 실행용 프롬프트만 작성
   - 조사 질문 / 기간 / 지역 / 우선 출처 / 제외 출처 / 원하는 표 / 중단 조건
6. 이미지가 필요하면 생성하지 말고 16:9 임원 보고용 이미지 프롬프트만 작성

출력 제목: YYYY-MM-DD | B제품 출시 일일 리스크 브리핑
출력 순서: 5줄 요약 → 변화 표 → 오늘 액션 → 고급 기능 실행 후보 → 확인한 URL
